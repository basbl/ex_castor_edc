    CastorEDC.RateLimit (ExCastorEDC v1.0.0)

    Copy Markdown View Source

    Keeps track of the API's rate limits.

    The API limits requests per user and per route, in fixed windows of ten minutes: 6,000 requests per route on data.castoredc.com, and fewer on some other servers. A route is a resource, so listing participants and fetching one draw from the same allowance. Every response says how much is left in these headers:

    • X-RateLimit-Limit - requests allowed in the window
    • X-RateLimit-Remaining - requests left in it
    • X-RateLimit-Retry-After - when the window resets, as a Unix timestamp (not a number of seconds, as Retry-After would be)

    The client records them for every route it uses, per server and credentials.

    Before a request, the client checks its route. When the last response said nothing is left and the window hasn't reset yet, it waits for the reset (plus up to a quarter of a second, so waiting processes don't all fire at once) instead of sending a request the API would refuse. Each wait emits a [:castor_edc, :rate_limit, :wait] telemetry event, with the wait in milliseconds as :duration and the :bucket and :base_url as metadata.

    When the API answers 429 anyway (other processes or machines may share the allowance), the client waits until the window resets (plus the same jitter) and sends the request again, at most three times, as long as the wait is within :max_rate_limit_wait (60 seconds by default). A 429 whose headers say requests remain isn't about the rate limit (batch exports answer one when too many run at once), and is returned as is. A 429 is refused before anything happens, so this is safe for any request. With rate_limit: :error, or when the wait would be longer, the client doesn't wait: a request it knows would be refused isn't sent and returns a CastorEDC.Error with code: :rate_limited, and a 429 is returned as is; either way the error's retry_after says how many seconds are left. Both options are given to CastorEDC.new/1.

    The client only knows what this node has seen. Several nodes sharing credentials still get the 429 handling.
