# AGENTS.md

ExCastorEDC (`:ex_castor_edc`, modules under `CastorEDC`) is an Elixir client for the Castor EDC API, built on Req.
Most of the client is generated from a corrected OpenAPI document; a hand-written core handles authentication, rate limits, paging, errors, exports and decoding.
`CONTRIBUTING.md` is the source for the workflow below; read it too.

## Layout

- `lib/castor_edc.ex` and the hand-written core in `lib/castor_edc/`: `client.ex`, `auth.ex` (+ `auth/secret.ex`), `rate_limit.ex`, `pagination.ex`, `page.ex`, `error.ex`, `export.ex` (+ `export/request.ex`), `field_value.ex`, `missing_value.ex`, `partial_date.ex`, `tabular.ex`, `model.ex`, `test.ex`, `application.ex`.
- Generated, never edit by hand: the endpoint modules in `lib/castor_edc/` (`participants.ex`, `data_points.ex`, `studies.ex`, …) and every struct in `lib/castor_edc/model/`.
  They start with `# This file is generated by mix castor_edc.gen.client`.
- `priv/openapi/upstream.json` is the published spec as fetched, `overlay.yaml` our corrections to it (an OpenAPI Overlay 1.0 document), and `castor_edc.json` the result the client is generated from.
- `gen/` holds the generator (`CastorEDC.Generator` and `gen/castor_edc/generator/`, with EEx templates) and the Mix tasks `castor_edc.spec.fetch`, `castor_edc.spec.build`, `castor_edc.gen.client`, `castor_edc.fixtures.record` and `castor_edc.e2e.seed`.
  It is compiled in `:dev` and `:test` only, isn't packaged and is filtered out of the docs.
- `test/` has unit tests, `test/fixtures/` (recorded responses), `test/support/` (`CastorEDC.Case`, `CastorEDC.E2ECase`) and the end-to-end suite in `test/e2e/`.
- `notebook/getting_started.livemd` and `guides/migrating-to-1.0.md` are ExDoc extras, as are the README and CHANGELOG.

## Changing the generated client

1. Change `priv/openapi/overlay.yaml` (a spec correction) or the generator in `gen/` (how code is produced).
   Every overlay action has a `description` saying why it exists; write one for each action you add.
   A target that selects nothing fails the build.
2. Run `mix castor_edc.spec.build` (applies the overlay to `upstream.json`, writes `castor_edc.json`).
3. Run `mix castor_edc.gen.client` (rewrites the endpoint modules and models, deletes the ones the spec no longer calls for).
4. Commit `castor_edc.json` and the regenerated files in the same commit as the overlay or generator change.

`mix quality` runs both tasks with `--check` and fails when the committed files aren't what the spec produces.
Don't run `mix castor_edc.spec.fetch` unless asked: it makes a network request, and a weekly CI job (`spec-drift.yml`) does it and opens an issue on drift.

## Core conventions

- A client is a `Req.Request` built by `CastorEDC.new/1`, from options, the application environment or `CASTOR_EDC_*` environment variables; client state lives in Req private keys (such as `:castor_edc_time_zone`).
- Every operation returns `{:ok, result} | {:error, %CastorEDC.Error{}}` and has a `!` variant that returns the result or raises the error.
- Paged collections return a `CastorEDC.Page` and have a `stream_*` function that pages lazily through `CastorEDC.Pagination`.
- Responses decode into structs under `CastorEDC.Model`; a field the spec doesn't name is kept under its wire name in the struct's `extra` map, and a value that can't be cast stays as it arrived instead of raising.
- `CastorEDC.Error` has `body` and `details` only for what the API sent; errors the client makes itself use its own codes and fields (`export_ids`, `result`).
- The API's times without a zone are local to the server, and each server has one fixed zone.
  `CastorEDC.time_zone/1` returns it: built in for the public servers, set with `:time_zone` (or `CASTOR_EDC_TIME_ZONE`) for a private one, `nil` when unknown.
  Never assume `Europe/Amsterdam`.
- Machinery the generated modules use but users shouldn't (`CastorEDC.Client.request/2`, the `CastorEDC.Model` helpers, `CastorEDC.RateLimit.lookup/1`) is `@doc false`, with a `#` comment above it explaining it instead.
- Never log or show secrets: a client's inspect output redacts the client secret, and tokens are cached per client ID and a hash of the secret.

## Checking your work

- `mix precommit` (test env): `compile --warnings-as-errors`, `deps.unlock --unused`, `format`, `credo --strict`, `coveralls`.
  Lefthook runs it as the pre-commit hook.
- `mix quality` (dev env): `hex.audit`, `format --check-formatted`, `credo --strict`, `dialyzer`, `deps.audit`, the two generator `--check`s and `docs --warnings-as-errors`.
- CI runs `mix compile --warnings-as-errors`, `mix coveralls` and `mix quality`.
- Judge them by their exit code.
  Never pipe them into `tail`, `head` or `grep`: the pipeline's status hides a failure.
- `mix coveralls` fails below 80% (`coveralls.json`); `test/support` and the test study tooling in `gen/` are left out of the count.
- Line length is 120 for both the formatter (with the Styler plugin) and Credo's `MaxLineLength`; let `mix format` decide layout.
- Credo runs strict: every module needs a `@moduledoc` (or `@moduledoc false`), and `TODO` tags fail it.
- Dialyzer uses PLTs in `priv/plts` and `.dialyzer_ignore.exs`; fix a warning rather than adding to the ignore file.

## Tests

- Unit tests never touch the network.
  Use `CastorEDC.Test.client/2` (or `CastorEDC.Case`, which delegates to it): only the Req adapter is replaced, so authentication, rate limiting and decoding still run, and `CastorEDC.Test.requested/0` returns the request that was sent.
- `test/fixtures/<operationId>.json` with `<operationId>.meta.json` are responses recorded from a test study by `mix castor_edc.fixtures.record`, with personal data replaced.
  Read them with `fixture/1` from `CastorEDC.Case`, and commit a re-recording on its own.
- `CastorEDC.FixtureContractTest` decodes every fixture through the generated client and fails when anything ends up in `extra`, or when the generated function sends another request than the recorded one.
  Fix that by describing the field in the overlay, or by recording the fixture again.
- `CastorEDC.PackageTest` checks that every file read at compile time is in the package's `files`.
- The end-to-end suite in `test/e2e/` is tagged `:e2e`, excluded by default and not run in CI: `mix test --only e2e`.
  It needs `CASTOR_EDC_CLIENT_ID`, `CASTOR_EDC_CLIENT_SECRET` and `CASTOR_EDC_STUDY_ID`, and optionally `CASTOR_EDC_BASE_URL` (see `.env.example`; `.env` is ignored).
  It writes to the study, seeds it on the first run (`mix castor_edc.e2e.seed`) and records the seeded IDs in the ignored `test/e2e/.seeded/`.
- Never commit credentials, study IDs, or hostnames of private environments, in code, tests, fixtures, docs or commit messages.

## Commits

- Each commit is one logical change that passes `mix precommit` on its own; tooling, mechanical changes, behaviour changes and deletions go in separate commits.
- A commit that adds behaviour includes its tests.
- Replacements take three steps: add the new beside the old, move callers over, delete the old.
- Subjects are imperative, sentence case, without a prefix or trailing full stop (`Know each server's time zone instead of assuming Amsterdam`).
- The body, wrapped at about 72 columns, explains why: what was wrong or missing, and what the change does about it; a list of `-` items for several related changes.
- A user-visible change adds an entry to `CHANGELOG.md` under `## Unreleased` (`Added`, `Changed`, `Fixed`; **Breaking:** where it is) in the same commit, naming the functions and options it affects.
- Don't commit or push unless asked; pull requests are merged without squashing.

## Docs and prose

- Markdown prose (README, CHANGELOG, guides, notebook) has one sentence per line, with no fixed-column wrapping.
- Moduledocs and docs are plain prose that says what a function returns and when it raises, with examples where they help; the generated docs come from the spec and the templates in `gen/`, so fix them there.
- `mix docs --warnings-as-errors` must pass.
  When the CHANGELOG or a guide names a function that no longer exists, add it to `skip_code_autolink_to` in `mix.exs` instead of rewording history.
- New public core modules go into `groups_for_modules` in `mix.exs`.
- Livebook saves the local setup into a notebook when it's saved there; check the diff of `notebook/` and commit only the intended changes.

## Gotchas

- `CastorEDC.Export.Request` reads `priv/openapi/castor_edc.json` at compile time (as an `@external_resource`) to check export formats, filters and options, so that file must stay in the package's `files`.
- The generator only generates models for schemas a successful response reaches.
  A schema only used in a request body gets no struct; its fields are listed in the operation's docs instead, so don't link to a `CastorEDC.Model` struct for it.
- A schema change in the overlay can rename or remove models and functions; check the regenerated diff, and the CHANGELOG, for user-visible changes.
- `hex.audit` has to stay first in `quality`: once another task has loaded the project's code paths, Mix no longer finds Hex's tasks.
- Times without a zone decode to `NaiveDateTime`s in the server's time, and export date-time filters move a `DateTime` to the server's zone, raising when it's unknown.
